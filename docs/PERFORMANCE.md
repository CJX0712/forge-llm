# PERFORMANCE · 性能基准与实测数据

> 全部数据由 `node cli/forge.mjs bench` 在本机实测采集，可一键复现。
> 机器：Windows x64 · Node **v22.22.2** · 2026-10-25。
> 绝对数值随机器而变；**相对比较与方法论**才是可移植的结论。

## 0. 计时方法论（先读这节）

本机存在持续性 CPU 抖动 —— 实测同一个 3e6 次整数累加的忙循环，单次耗时在
**3.9 ms ~ 25.6 ms** 之间波动（6.5× 方差）。在这种环境里，朴素的
「跑 N 次取平均」会得到毫无意义的数字。因此本基准采用三条纪律：

1. **充分预热后取最小单次耗时**（best-of-N）。取最小值而非平均值：均值会被
   GC 暂停与 OS 调度抖动抬高；而最小值对应「未被干扰的那一次」。
   预热不足同样致命 —— 曾实测到 Q4_K 比 Q8_0 慢 25× 的假象，根因是 JIT
   尚未完成优化（解释器 → Sparkplug → Maglev → TurboFan 需要成百次调用）。
2. **对比项交错计时**（A/B/A/B…）。让两个被测实现处于相同的机器状态
   （频率、缓存、GC 相位），全局 throttling 同等地影响双方，相对比较不受影响。
3. **控制内存占用**。大张量用完即释放；64MB 级分配会改变堆状态，
   曾污染后续节的计时。

## 1. GEMM（B1）—— 4 路展开 vs 朴素三重循环

| 形状 | 展开版 | 朴素版 | 加速比 | GFLOPS（展开/朴素） | 与参考实现一致性 |
|---|---|---|---|---|---|
| 128×256×256 | 7.34 ms | 10.34 ms | **1.41×** | 2.28 / 1.62 | relL2 = **0**（比特级一致） |
| 512×1024×1024 | 497.75 ms | 638.05 ms | **1.28×** | 2.16 / 1.68 | relL2 = **0**（比特级一致） |

**选型记录：缓存分块被实测否决。** cache blocking 是 C/BLAS 的标准手段，
本实现最初也采用 `BK=32, BN=32` 分块。但在 512×1024×1024 上做交错基准
（best-of-60，4m49s）后，数据推翻了惯例：

| 实现 | 耗时 | GFLOPS |
|---|---|---|
| **朴素 + 4 路展开（采用）** | **433.9 ms** | **2.47** |
| BK=64, BN=64 分块 | 508.2 ms | 2.11 |
| BK=32, BN=32 分块 | 512.1 ms | 2.10 |
| BK=128, BN=32 分块 | 531.2 ms | 2.02 |
| 朴素三重循环（无展开） | 567.3 ms | 1.89 |

结论：在 V8 生成的 JS 代码上，访存模式与寄存器分配由 JIT 决定，分块只增加
循环开销与 C 矩阵的多次读写。**JS 下最快的是最简形式。** 若未来接入
WASM/SIMD，L0 是单一替换点（`src/L0/numeric.js` 的 `gemm`/`matvec`）。

## 2. matvec（B2）—— 解码热点

4096×2048 单矩阵乘向量：**6.38 ms / 2.63 GFLOPS**。
这是每生成一个 token 就要走一遍的路径（一层投影的 FLOPs = 2·N·K）。

## 3. 量化格式（B3）—— 精度/体积/速度的三角

n = 4096，x ~ N(0, 0.7)，与 `y` 点积。位布局对齐 llama.cpp（GGUF）。

| 格式 | bpw | 压缩比 | RMSE | cos | 解码速度 | GFLOPS |
|---|---|---|---|---|---|---|
| F16 | 16 | 2× | 1.47e-4 | 1.000000 | 1.78 ns/元素 | 1.12 |
| Q8_0 | 8.5 | 3.76× | 3.71e-3 | 0.999986 | **1.32 ns/元素** | 1.52 |
| Q6_K | 6.5625 | 4.88× | 1.23e-2 | 0.999850 | 2.25 ns/元素 | 0.89 |
| Q4_K | 4.5 | 7.11× | 5.44e-2 | 0.997087 | **1.29 ns/元素** | 1.55 |

要点：
- **Q8_0 / Q4_K 比 F16 更快** —— 解码时每元素搬运的字节更少（8.5/4.5 bit vs
  16 bit），内存带宽是瓶颈而非计算。
- **Q4_K 与 Q8_0 同速**（1.29 vs 1.32 ns/元素）：Q4_K 的 nibble 解包 + 6-bit
  scale 查找被 4.5 bpw 的带宽优势抵消。这是纯 JS 下的实测结论。
- 精度排序符合理论：Q8_0 几乎无损（cos 0.99999），Q4_K 有明显但可控的损失
  （cos 0.997，RMSE 5.4e-2）。
- 工程教训：Q4_K 内循环最初通过「每次调用返回新数组」的辅助函数解 6-bit
  scale，在大堆下频繁触发增量 GC，实测慢 25×。改为零分配的 out-param 变体
  （`getScaleMinK4Into`）后恢复至 1.3 ns/元素。**热点路径上的每次分配都是
  性能bug。**

## 4. 注意力（B4）—— 三种单 query 行实现

seq=512, d=64，交错计时（best-of-100）：

| 实现 | 耗时 | 说明 |
|---|---|---|
| flash（在线 softmax） | 0.0820 ms | O(d) 内存，无分配 |
| naive（物化 scores） | 0.0744 ms | 每次调用分配 O(n) |
| **decode（两趟扫描 + 复用 scratch）** | **0.0779 ms** | O(n) 可复用缓冲，零分配 |

三者数值等价（maxErr = 1.19e-7，源于求和顺序不同）。

**结论与选型**：单 query 行下三者计算量同为 O(n·d)，差距 <10%。在线 softmax
的价值在内存（O(d) vs O(n)）与批处理/prefill 场景，而非单行速度；naive 最快
但每次调用分配。L6 解码路径采用 **decode 版**：零分配 + 一致略快于 flash
（1.05×），并在多轮测量中稳定（512/2048/8192 三个长度上均领先约 5%）。

## 5. 端到端推理（B5）

模型：dim=256, hidden=512, layers=4, heads=8/4 (GQA), vocab=4096，**3.41M 参数**。

| 指标 | 数值 |
|---|---|
| prefill 32 token | 97.4 ms → **329 tok/s** |
| decode（单 token） | 3.73 ms → **268 tok/s** |

decode 路径上的两项关键优化（均有前后实测）：
- **GQA K/V 收集去重**：同一 kv-head 服务 groupSize 个 q-head，K/V 收集从
  「每 q-head 一次」改为「每 kv-head 一次」—— decode 235 → 256 tok/s。
- **注意力实现换型**：在线 softmax → 两趟扫描零分配版（见 §4）。

## 6. 训练（B6）

dim=128, layers=2, seq=16, batch=1，361K 参数：
**25.96 ms/step**（前向 + 反向 + Adam），**616 tok/s**。

## 8. 诚实的边界

- 绝对 GFLOPS 受机器与 Node 版本影响，跨机器比较请以自己的实测为准。
- 本机 CPU 抖动可达 6.5×，单次运行的数字可能有 ±20% 偏差；本页数据为
  一次代表性运行，方法论（预热 + best-of-N + 交错）保证相对比较有效。
- 纯 JS 的天花板明显：接 WASM/SIMD 或 WebGPU 是数量级的跃升路径，
  架构上已隔离在 L0（数值内核）单一替换点。
